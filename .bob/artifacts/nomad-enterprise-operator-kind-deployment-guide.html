What Is a Kubernetes Operator?

An operator is a Kubernetes controller — a program that runs inside your cluster and automates complex, domain-specific management tasks. Instead of a human administrator manually creating resources and watching for failures, the operator does it continuously and automatically.

The Nomad Enterprise Operator watches for NomadCluster resources you create and then handles everything automatically: provisioning pods, generating TLS certificates, bootstrapping ACLs, and self-healing on failure. All the expertise of running Nomad is encoded in the operator itself.

Deployment Steps

1
Create a local Kubernetes cluster with kind
kind create cluster --name nomad-operator --image kindest/node:v1.31.0 --wait 120s

Why

Kubernetes requires a cluster to exist before anything can run in it. kind (Kubernetes in Docker) spins up a full Kubernetes control plane inside a Docker container — lightweight, disposable, and perfect for local development. We pinned v1.31.0 for reproducibility. The --wait flag blocks until the control plane is ready before proceeding.

Side effect: kubectl context is automatically switched to kind-nomad-operator.
2
Build the operator Docker image locally
make docker-build IMG=example.com/nomad-enterprise-operator:v0.0.1

Why

The operator is Go source code in this repository. It must be compiled into a Docker image before Kubernetes can run it. We built it locally rather than pulling the upstream image from Quay because we want to test the local source. The example.com/ prefix is a kubebuilder convention — a deliberately fake registry hostname that signals "this image is local-only and should never be pushed."

Side effect: config/manager/kustomization.yaml is rewritten by kustomize edit set image during make deploy to record the image name. This is intentional — it is how kustomize's image-override mechanism works and is expected to be a dirty file after a local deploy.
3
Load the image into the kind cluster
kind load docker-image example.com/nomad-enterprise-operator:v0.0.1 --name nomad-operator

Why

After building, the image exists only in your local Docker daemon. The kind cluster runs its own isolated container runtime inside Docker — it cannot see your local daemon's images. This command copies the image directly into the kind node so Kubernetes can use it without any network pull. Without this step, the operator pod would fail with ImagePullBackOff.

4
Install cert-manager
kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.16.3/cert-manager.yaml

Why

cert-manager is a commonly expected cluster dependency and is installed by the project's e2e test suite. It is not strictly required by this operator — the Nomad Enterprise Operator generates its own CA and TLS certificates internally without invoking cert-manager. We installed it because it is a standard cluster component and the operator's test infrastructure expects it to be present.

Note: cert-manager support in the operator's kustomize config (config/default/kustomization.yaml) is explicitly commented out. The operator handles certificate lifecycle itself.
5
Deploy the operator controller manager
make deploy IMG=example.com/nomad-enterprise-operator:v0.0.1

Why

This is the step that actually installs the operator into the cluster. Under the hood it runs kustomize build config/default | kubectl apply, which creates:

  • The 3 CRDs — NomadCluster, NomadSnapshot, NomadAutoscaler
  • The controller manager Deployment — the operator pod itself
  • RBAC — ClusterRoles and bindings so the operator can create/update/delete the resources it manages
  • A metrics Service for Prometheus scraping
  • The nomad-enterprise-operator-system namespace

Once the pod is running, the operator is idle — watching for NomadCluster resources but not yet doing anything, because none exist yet.

6
Create the namespace and license secret
kubectl create namespace nomad
kubectl create secret generic nomad-license \
  --from-literal=license="<license-string>" \
  --namespace nomad

Why

The operator only creates its own system namespace. The namespace where your NomadCluster lives must be created manually first. The license secret must exist before the CR is applied because the operator reads it immediately during reconciliation — a missing secret causes the reconcile to fail. The Nomad Enterprise license is the only required field for a NomadCluster; everything else has an operator-managed default.

7
Apply the NomadCluster custom resource
kubectl apply -f config/samples/minimal/nomadcluster.yaml --namespace nomad

Why

This is the signal to the operator to begin work. A NomadCluster CR is the declaration of intent — "I want a Nomad cluster with these settings." The operator detects it via a watch and immediately begins reconciling. The minimal sample uses type: NodePort for the external service, which is correct for kind — the default LoadBalancer type would wait indefinitely for an external IP that kind cannot provide without MetalLB.

8
Operator reconciles — what happened automatically

Phase progression

Creating → ACLBootstrap → Running (3/3)

Resources created by the operator

  • StatefulSet with 3 replicas (nomad-0, nomad-1, nomad-2)
  • 3 Services — headless (service discovery), internal (ClusterIP), external (NodePort)
  • PodDisruptionBudget — max 1 unavailable, protecting quorum
  • Role + RoleBinding for the Nomad pods

Why Operators Matter

Manual ApproachOperator Approach
Create each pod by handOperator provisions all nodes on demand
Generate and rotate certificates manuallyOperator manages the full certificate lifecycle
Run ACL bootstrap commands after cluster startsOperator detects readiness and bootstraps automatically
Recreate pods if they crashOperator detects and repairs drift continuously

Next Steps

  • Retrieve the bootstrap ACL token: kubectl get secret nomad-acl-bootstrap -n nomad -o jsonpath='{.data.token}' | base64 -d
  • Access the Nomad UI via the NodePort on the kind node IP (port shown by kubectl get svc nomad-external -n nomad)
  • Deploy a NomadSnapshot CR to enable scheduled Raft snapshots
  • Deploy a NomadAutoscaler CR to enable the Nomad Autoscaler agent
  • Tear down when done: kind delete cluster --name nomad-operator
